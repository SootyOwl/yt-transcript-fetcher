# Test Results: bgutil-pot Rust Utility for PoToken Generation

## Date: 2026-03-07

## Summary

Manually tested the [bgutil-ytdlp-pot-provider-rs](https://github.com/jim60105/bgutil-ytdlp-pot-provider-rs) v0.7.2 Rust binary for PoToken generation and evaluated its effectiveness in resolving YouTube InnerTube API `FAILED_PRECONDITION` errors for transcript fetching.

## Environment

- Platform: Linux x86_64
- Binary: `bgutil-pot-linux-x86_64` v0.7.2 (~51MB)
- Test video: `dQw4w9WgXcQ` (Rick Astley - Never Gonna Give You Up)

## Test Results

### 1. bgutil-pot Token Generation: PASS

The Rust binary successfully generates PoTokens in sub-second time:

```
$ ./bgutil-pot --content-binding "dQw4w9WgXcQ" --verbose

Generated real TokenMinter - expires at: 2026-03-07 23:55:01 UTC, lifetime: 43200s
Generated POT token: MlVtQW56y6OO7W1_0mhel1co5MP9WY...
```

**Key metrics:**
- Token generation: <1 second (with caching, even faster)
- Memory: <50MB RSS
- Cache: 6-hour TTL, stored at `~/.cache/bgutil-ytdlp-pot-provider/cache.json`
- Both CLI and HTTP server modes work correctly

**Server mode API:**
```
POST /get_pot {"content_binding": "dQw4w9WgXcQ"}
→ {"poToken": "...", "contentBinding": "dQw4w9WgXcQ", "expiresAt": "..."}

GET /ping → {"server_uptime": 120, "version": "0.7.2"}
```

**Note:** The server does NOT return `visitor_data` in responses — only `poToken`, `contentBinding`, and `expiresAt`.

### 2. Current Android Client (19.09.37): FAIL

Both `/player` and `/get_transcript` endpoints now return `400 FAILED_PRECONDITION`:

```
[/player]          HTTP 400 - FAILED_PRECONDITION
[/get_transcript]  HTTP 400 - FAILED_PRECONDITION
```

**Conclusion:** The Android 19.09.37 client is completely broken. YouTube has expanded PoToken enforcement to cover all clients including older Android versions.

### 3. WEB Client + PoToken: FAIL

Multiple approaches tested, all failed:

| Approach | /player Result | /get_transcript Result |
|----------|---------------|----------------------|
| WEB + PoToken (no cookies) | UNPLAYABLE | FAILED_PRECONDITION |
| WEB + PoToken + API key + Origin headers | UNPLAYABLE | FAILED_PRECONDITION |
| WEB + PoToken + page cookies + page visitorData | UNPLAYABLE | FAILED_PRECONDITION |
| WEB + session-bound PoToken (bound to visitorData) | UNPLAYABLE | FAILED_PRECONDITION |
| WEB + content-bound PoToken (bound to videoId) | UNPLAYABLE | FAILED_PRECONDITION |
| MWEB + PoToken | UNPLAYABLE | N/A |

**Root cause analysis:** The PoToken is generated by bgutil-pot's internal BotGuard session, which has its own `visitorData`. When we send the PoToken with a *different* `visitorData` in our API request, YouTube detects the mismatch and rejects it. The Rust server does not expose its internal `visitorData`, making it impossible to construct a matching request context.

The WEB client's "UNPLAYABLE" response (even with cookies from visiting the YouTube page) confirms that the WEB InnerTube API now requires a PoToken that is cryptographically bound to the same session context used in the request.

TVHTML5_SIMPLY_EMBEDDED_PLAYER: "YouTube is no longer supported in this application or device."

### 5. ANDROID_VR Client: PASS (for /player)

The ANDROID_VR client still works for the `/player` endpoint without PoToken:

```
[/player]          HTTP 200 - Playability: OK, Caption tracks: 6
[/get_transcript]  HTTP 400 - FAILED_PRECONDITION
```

This is the same approach yt-dlp uses. The key insight is that yt-dlp:
1. Uses ANDROID_VR client for `/player` to get caption track metadata
2. Extracts signed `/api/timedtext` URLs from the player response
3. Fetches subtitles directly via those signed URLs (no PoToken needed)
4. Does NOT use the InnerTube `/get_transcript` endpoint at all

## Conclusions

### Why bgutil-pot PoTokens Don't Work for Direct API Calls

The PoToken system is designed to attest that a request comes from a genuine client environment. The token is:
1. Generated by BotGuard's JavaScript VM running inside bgutil-pot
2. Signed using the BotGuard session's internal state (including its own `visitorData`)
3. Validated by YouTube against the `visitorData` in the API request context

Since bgutil-pot generates its own internal `visitorData` and does NOT expose it, we cannot construct an API request where the `visitorData` matches the PoToken's session. This creates an inherent mismatch that YouTube detects.

**yt-dlp solves this differently:** It uses the PoToken provider as a *plugin* within its extraction pipeline, where it manages the full session lifecycle including `visitorData` propagation. This tight integration is not available to standalone API callers.

### Recommended Path Forward

1. **Short-term fix (v1.x):** Switch from Android 19.09.37 to **ANDROID_VR** client for `/player`, then fetch subtitles via signed `/api/timedtext` URLs instead of `/get_transcript`. This requires:
   - Parsing caption track URLs from `/player` response
   - Fetching subtitle content from timedtext URLs (VTT/srv3/json3 format)
   - Converting timedtext format to our `Transcript`/`Segment` models
   - No PoToken or external dependencies needed

2. **Medium-term (v2.0):** Implement Option B from the investigation doc (external PoToken server integration) with the Rust server, BUT require the server to also provide `visitorData` — this may require a PR to the Rust project or using the TypeScript server instead.

3. **Long-term:** Monitor yt-dlp's approach and adapt. If ANDROID_VR gets blocked, fall back to the PoToken server approach with proper session management.
