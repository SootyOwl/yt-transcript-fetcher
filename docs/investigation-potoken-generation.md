# Investigation: PoToken Generation for YouTube InnerTube API

## Date: 2026-03-07

## Background

YouTube has enforced PoToken (Proof of Origin Token) requirements on the `get_transcript` and `/player` InnerTube endpoints. Our library currently uses the ANDROID client v19.09.37, which previously didn't require attestation, but YouTube has now expanded enforcement to cover all clients including older Android versions. This results in `400 FAILED_PRECONDITION` errors on all API calls.

## What is a PoToken?

A **Proof of Origin (PO) Token** is a cryptographic attestation parameter that YouTube requires to verify requests come from genuine clients rather than automated bots. It is generated by:

- **BotGuard** (Web clients)
- **DroidGuard** (Android clients)
- **iOSGuard** (iOS clients)

Tokens from one platform cannot be used on another. The token generation involves running Google's obfuscated VM bytecode (BotGuard) which performs environment checks and produces a signed attestation response.

### Token Types

1. **Session-bound token**: Tied to `visitorData` (logged out) or Data Sync ID (logged in). Reused across requests within a session.
2. **Content-bound token**: Tied to a specific Video ID. Generated per-request for `/player` and `/get_transcript` calls. Cannot be cached.

### What Requires PoTokens Now

Per the [yt-dlp PO Token Guide](https://github.com/yt-dlp/yt-dlp/wiki/PO-Token-Guide):

| Client    | Requirement               |
|-----------|---------------------------|
| `web`     | Subs (rolling out), GVS   |
| `mweb`    | GVS only                  |
| `android` | GVS or Player             |
| `ios`     | GVS or Player             |
| `tv`      | Not required              |

**Critically**: [yt-dlp issue #13075](https://github.com/yt-dlp/yt-dlp/issues/13075) confirms that **subtitles/transcripts now require PoTokens** on web clients. The `/api/timedtext` endpoint now validates `pot=` parameters, and the InnerTube `get_transcript` endpoint requires attestation in the request context.

## How PoToken Generation Works

The generation pipeline (as reverse-engineered by [LuanRT/BgUtils](https://github.com/LuanRT/BgUtils)):

### Step 1: Fetch BotGuard Challenge
Request challenge data from YouTube's Web Anti-Abuse API:
```
POST https://jnn-pa.googleapis.com/$rpc/google.internal.waa.v1.Waa/Create
```
This returns a VM script (JavaScript interpreter) and a bytecode program.

### Step 2: Execute BotGuard VM
Load the interpreter script in a JavaScript environment. The VM needs a "good enough" DOM implementation (e.g., jsdom for Node.js). Execute the bytecode program to obtain snapshot functions.

### Step 3: Generate Integrity Token
Call the snapshot function, which runs environment checks and produces a BotGuard response. Exchange this response for an integrity token:
```
POST https://jnn-pa.googleapis.com/$rpc/google.internal.waa.v1.Waa/GenerateIT
```

### Step 4: Mint the PoToken
Use the integrity token with a minter callback to produce the final PoToken (~110-128 bytes, base64-encoded). The minter accepts an identifier (Video ID for content-bound tokens, Visitor ID for session-bound tokens).

**Key constraint**: This entire process requires a JavaScript runtime (Node.js, Deno, Bun, or a browser) because BotGuard is distributed as obfuscated JavaScript bytecode.

## Existing Implementations

### 1. [bgutils-js](https://www.npmjs.com/package/bgutils-js) (npm, by LuanRT)
- **Latest**: v3.2.0
- Core library that interfaces with BotGuard's API
- < 4KB, works in Node.js/Deno/Bun/browsers
- Requires jsdom (or similar) in Node.js for DOM implementation
- **Known issue**: Memory leak (~25MB/request) due to jsdom/V8 isolate management

### 2. [bgutil-ytdlp-pot-provider](https://github.com/Brainicism/bgutil-ytdlp-pot-provider) (TypeScript HTTP server)
- Runs as HTTP server on port 4416
- `POST /get_pot` with `{"content_binding": "<video_id>"}` → returns `{"po_token": "...", "visitor_data": "..."}`
- Requires Node.js >= 20 or Deno >= 2.0
- Used by yt-dlp as a plugin

### 3. [bgutil-ytdlp-pot-provider-rs](https://github.com/jim60105/bgutil-ytdlp-pot-provider-rs) (Rust rewrite)
- Single binary, no runtime dependencies
- Sub-second token generation with caching (6hr TTL)
- < 50MB RAM usage
- Same HTTP API as TypeScript version
- **Recommended for new deployments**

### 4. [pytubefix](https://github.com/JuanBindez/pytubefix) approach
- Bundles a webpack-packaged version of BgUtils as `botGuard.js`
- Calls Node.js via subprocess: `node botGuard.js <visitorData>`
- Falls back gracefully if Node.js unavailable
- Uses [nodejs-wheel-binaries](https://pypi.org/project/nodejs-wheel-binaries/) for pip-installable Node.js

## Options for yt-transcript-fetcher

### Option A: Bundle a Node.js PoToken Generator Script (pytubefix approach)

**How**: Bundle a webpack-packaged `botGuard.js` script. Call it via `subprocess` with `node`, passing `visitorData` and `videoId`. Parse the JSON output for the PoToken.

**Pros**:
- Self-contained — no external server required
- Proven approach (pytubefix uses this in production)
- Can use `nodejs-wheel-binaries` pip package so users don't need to install Node.js separately

**Cons**:
- Introduces Node.js as a dependency (even if auto-installed via pip)
- Must maintain/update the bundled BotGuard script as YouTube changes
- Memory leak risk from jsdom (~25MB per generation)
- Subprocess overhead per token generation
- Significant increase in package size

**Complexity**: Medium-High

### Option B: External PoToken Server Integration

**How**: Support an optional `po_token_server_url` parameter. If configured, make HTTP requests to `POST /get_pot` on the bgutil server (TypeScript or Rust) to obtain tokens before API calls.

**Pros**:
- No Node.js dependency in the Python package
- Leverages well-maintained external tools (especially the Rust version)
- Token caching handled by the server (6hr TTL)
- Clean separation of concerns
- Sub-second performance with Rust server

**Cons**:
- Requires users to run an external server
- More complex setup for end users
- Network dependency between Python library and token server

**Complexity**: Low (implementation), Medium (user setup)

### Option C: Manual PoToken / Cookie Authentication

**How**: Accept user-provided PoTokens and/or YouTube cookies. Users extract tokens from their browser's developer tools.

**Pros**:
- No additional dependencies
- Works immediately
- Simplest implementation

**Cons**:
- Poor user experience — manual extraction is tedious
- Tokens expire (content-bound tokens are per-video, session tokens expire)
- Not viable for automated/production use cases

**Complexity**: Low

### Option D: Hybrid Approach (Recommended)

**How**: Implement a layered strategy:
1. **Primary**: Support external PoToken server (Option B) — zero new dependencies, best for production
2. **Secondary**: Support bundled Node.js generator (Option A) — better UX for development/casual use
3. **Fallback**: Accept manual PoTokens (Option C) — always available escape hatch
4. **Graceful degradation**: If no PoToken source is configured, attempt the request anyway and raise a clear `PoTokenRequired` error with setup instructions

**Pros**:
- Maximum flexibility for different use cases
- No mandatory new dependencies (server and manual modes)
- Optional convenience dependency (Node.js for auto-generation)
- Clear error messages guide users to solutions

**Cons**:
- More code to maintain
- Need documentation for all modes

**Complexity**: Medium

## Recommendation

**Start with Option B (External Server) + Option C (Manual) as v2.0.**

Rationale:
- The external server approach adds zero new dependencies to the Python package
- The Rust-based server ([bgutil-ytdlp-pot-provider-rs](https://github.com/jim60105/bgutil-ytdlp-pot-provider-rs)) is a single binary with excellent performance
- Docker images are available for easy deployment
- Manual token support is trivial to implement as a fallback
- Option A (bundled Node.js) can be added later as an optional `[potoken]` extra dependency

### Proposed API Design

```python
from yt_transcript_fetcher import YouTubeTranscriptFetcher

# Option B: External server (recommended for production)
fetcher = YouTubeTranscriptFetcher(
    po_token_server="http://127.0.0.1:4416"  # bgutil server
)

# Option C: Manual tokens
fetcher = YouTubeTranscriptFetcher(
    po_token="<base64-token>",
    visitor_data="<visitor-data>"
)

# No PoToken: attempts request, raises PoTokenRequired on failure
fetcher = YouTubeTranscriptFetcher()
```

### Implementation Steps

1. Add `PoTokenRequired` exception
2. Add `po_token_server` parameter to `YouTubeTranscriptFetcher.__init__`
3. Add `po_token` / `visitor_data` manual override parameters
4. Create `_get_po_token(video_id)` method that:
   - Returns manual token if provided
   - Calls external server if configured
   - Returns `None` if neither configured
5. Modify `get_transcript()` to include PoToken in request context
6. Switch client to `WEB` (since we'll have PoTokens to pass)
7. Handle `FAILED_PRECONDITION` → raise `PoTokenRequired` with helpful message
8. Update documentation with setup instructions

### Where PoToken Goes in the Request

For InnerTube API calls, the PoToken is included in the request context:

```json
{
    "context": {
        "client": {
            "clientName": "WEB",
            "clientVersion": "2.20250305.01.00",
            "visitorData": "<visitor_data>"
        }
    },
    "serviceIntegrityDimensions": {
        "poToken": "<po_token>"
    },
    "params": "<protobuf_params>"
}
```
